# Assets and run-time dependencies of the gorge world

All world geometry and textures (terrain, walls, wash, vegetation, boulders, rocks, fires, their
thermal textures) are generated by the scripts in this directory (`gorge.py`) from a seed. Nothing
is downloaded, and nothing is taken from a texture pack, a game asset pack, a website or
`pybullet_data`. The ground plane `plane.urdf` that gym-pybullet-drones' `BaseAviary._housekeeping`
loads from `pybullet_data` is not loaded: `fly_gorge.GorgeAviary` replaces that method with the same
housekeeping minus the plane. The flames, smoke, firelight, sky (gradient, clouds) and the thermal false-color palette are
written in code: the palette is ten hand-chosen control points, linearly interpolated
(`sensors.PALETTE`), and no vendor palette table is used. The reference photographs that guided the
2026-11-11 redesign are not in this repository and nothing is derived from their pixels. Text in the images uses DejaVu Sans from
Matplotlib's own data directory.

## Generated assets (`assets/`, seed 7 written as `*_s7*`; rewritten by the build from the seed)

The directory is not tracked by git (about 300 MB for seed 7). Any script that loads the world builds it when
the cache or one of its files is missing; `sim/setup.sh` runs the build once after the Python environments.

The build (`gorge.Gorge`, about 140 s) writes these and caches the world's data in `gorge_s7.pkl`; the key
is the seed plus a hash of gorge.py's source, so a changed generator rebuilds everything. Files of an
earlier build of the same seed that the current one does not write are removed. Nothing here is a
photograph, a crop of one or a downloaded texture: every texel is computed from the 3D point it covers
(noise fields, Voronoi patterns and baked lighting in code).

The gorge session's camera payload (`camera_component.py`) runs in its own private environment
`sim/world/.venv-video` (git-ignored; `fly_gorge_qgc.sh` makes it with uv), which holds only:

| dependency | used for | origin | license |
|---|---|---|---|
| PyAV 19.0.2 (wheel) | H.264 encoding (`libx264`, chosen by name; the bundled FFmpeg also contains Apple's VideoToolbox encoder, which is never used) and, in `test_camera.py`, FFmpeg's RTP demuxer and H.264 decoder | pypi.org/project/av, github.com/PyAV-Org/PyAV | BSD-3-Clause |
| FFmpeg 9.0 libraries, bundled in the PyAV wheel (`av/.dylibs`) | libavcodec, libavformat, libswscale | ffmpeg.org | LGPL-3.0-or-later (its build configuration: `--enable-version3`) |
| x264 (libx264.165, bundled in the PyAV wheel) | the H.264 encoder | videolan.org/x264 | GPL-2.0-or-later |
| NumPy 2.5.4 | frame buffers | numpy.org | BSD-3-Clause |

The MAVLink messages of the camera are packed by its own code (`camera_component.py`, layouts and
CRC_EXTRA from the MAVLink XML); `test_camera.py` checks them with pymavlink's generated dialect
(`sim/mavlink/.gen/apm2.py`, LGPL-3.0, the private test oracle of `sim/mavlink/`). `tile_server.py`
uses PyBullet, NumPy, SciPy and Pillow from the table above and Python's `http.server`; no map data,
font or image is downloaded. QGroundControl's own GStreamer decodes the streams on the ground side.

`wind.py`'s check (`python wind.py`) also builds run_leanfc's own environment as the reference for the
wind-off comparison; that reference environment (not the gorge world) loads the package's
`plane.urdf` from `pybullet_data`, as run_leanfc always does.
