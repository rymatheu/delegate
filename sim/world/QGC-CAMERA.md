# What QGroundControl 5.1.5 requires of a MAVLink camera, a video stream and a map tile server

Source: QGroundControl `v5.1.5`, exported read-only to `sim/mavlink/qgc-5.1.5/src` (as for
`sim/mavlink/QGC-REQUIREMENTS.md`, which covers the vehicle). Paths are relative to `src/`. The camera is
`sim/world/camera_component.py`, the streams its encoder and RTP sender, the map `sim/world/tile_server.py`.

Status codes: **impl** implemented and exercised by `sim/world/test_camera.py` or `test_tiles.py`;
**observed** also seen in the log of the real QGroundControl 5.1.5 (`sim/world/run_qgc_gorge.py`);
**stub** answered so that QGroundControl stops asking, with nothing behind it.

## Video: how QGroundControl configures and receives the streams

| # | QGroundControl (5.1.5 source) | needed | camera_component.py | status |
|---|---|---|---|---|
| 16 | `VideoManager/VideoManager.cc` `_createVideoReceivers`: two receivers, "videoContent" and "thermalVideo". `_videoSourceChanged` (connected to `QGCCameraManager::streamChanged`) gives the first the current stream and the second the thermal stream. `hasVideo`: `streamEnabled` (default true) and `streamConfigured` (true once the main stream has a uri: `autoStreamConfigured`); `_startReceiver` uses a 3 s timeout for UDP. | — | — | observed |
| 17 | `_updateAutoStream`: for VIDEO_STREAM_TYPE_RTPUDP (1) and an encoding other than H265, the source is "UDP h.264 Video Stream"; the receiver's URL is the uri itself when it contains `udp://`, else `udp://0.0.0.0:<uri>`; for the main receiver it sets the setting `videoSource` to that source (written to the settings file). It runs from the receiver's `videoStreamInfoChanged` handler (`_initVideoReceiver`) and again from `_updateSettings`. | type 1, encoding H264 (1), a uri | uri `udp://127.0.0.1:5600` and `udp://127.0.0.1:5602` (item 19) | impl, observed |
| 18 | `_updateSettings`, main receiver, after `_updateAutoStream`: with source "UDP h.264" the URL is set again from the setting `udpUrl` (default `0.0.0.0:5600`, `Settings/Video.SettingsGroup.json`), so the main stream must use the port of `udpUrl` (5600 unless the user changed it); the thermal receiver returns before this step and keeps its own URL. | main stream on 5600 | 5600; thermal on 5602 (an even port: receivers that open RTCP on port + 1, like FFmpeg, can take both) | impl, observed |
| 19 | `_videoSourceChanged` starts the receivers (`_restartAllVideos`) only when `_updateSettings` reports a change. But the `videoStreamInfoChanged` handler has already set the URL (item 17) before `_updateSettings` compares it, so with a bare port number nothing changes and no receiver is ever started (observed with uri "5600": URL `udp://0.0.0.0:5600` set at 8.7 s, no "Starting" in 75 s). QGroundControl then has written `videoSource` = UDP h.264, and from its next launch `_initVideoReceiver` starts the main receiver at once from that setting (observed), but the thermal receiver still never starts (observed). With a uri that differs from `udp://` + `udpUrl`, `_updateSettings` replaces it by the `udpUrl` URL, sees the change and restarts both receivers. | a URL other than `udp://0.0.0.0:5600` | `udp://127.0.0.1:PORT`: both receivers start and decode, on a fresh installation and with the setting already written (observed); a burst of receiver restarts at discovery (4 to 22 "Restart video receiver" requests within 10 ms in the runs so far), then steady. `--uri-form port` announces bare ports | impl, observed |
| 20 | `VideoReceiver/GStreamer/GstSourceFactory.cc` `buildUdpSource`: `udpsrc` on the URL with caps `application/x-rtp, media=video, clock-rate=90000, encoding-name=H264` (no payload type and no sprop-parameter-sets: SPS and PPS must come in band), 8 MiB buffer; `linkSourceToParser`: an `rtpjitterbuffer` (latency `rtpJitterLatencyMs`, default 80 ms; none in low-latency mode), then `parsebin` (rtph264depay, h264parse) and `decodebin3` (`GstVideoReceiver.cc` `_makeDecoder`). | RFC 6184 RTP, 90 kHz, SPS/PPS in band | payload type 96, single NAL unit packets up to 1200 bytes and FU-A above, marker bit on the last packet of a frame, SPS and PPS before every keyframe (x264 repeat-headers) | impl, observed |
| 21 | `GstVideoReceiver.cc` `_watchdog`, every second: no buffer from the source for the timeout (3 s) or no decoded frame for twice that: "Stream timeout" / "Video decoder timeout", and the receiver restarts. A decoder needs a keyframe to start. | a frame at least every 3 s; keyframes regularly | 15 and 8.7 fps; a keyframe every second (keyint = frame rate, scenecut off) | impl, observed |
| 22 | `FlyView/FlightDisplayViewVideo.qml`: the thermal video is drawn over the main video ("thermalItem"), by default blended (THERMAL_BLEND, opacity 85 %, `VehicleCameraControl` settings `thermalMode`, `thermalOpacity`), 85 % of the main video's height, centered, with the thermal stream's aspect ratio (its own field of view is not used); the camera control panel offers off, blend, full and picture in picture. | — | thermal 160 x 120, hfov 57 | not observable without the GUI |
