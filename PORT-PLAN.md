# Port plan: the rest of ArduCopter (estimation, vehicle logic, MAVLink)

Written 2026-11-11 against ArduPilot 802db19de1 (the pinned checkout `cpp2lean/ardupilot/src`) and the translator `cpp2lean.py` of 2026-11-04. Everything measured here was measured on a private clone under `build/survey/` (section 1 and appendix B); nothing in the ArduPilot checkout, the translator, `lean/` or `contracts/` was changed.

## 0. Summary

**What the finished port is.** ArduCopter built for one quad-X frame with the feature set the user asked for (STABILIZE boot mode, ALT_HOLD, GUIDED, AUTO with takeoff/waypoint/spline/land/RTL items, LOITER, BRAKE, RTL, LAND, CIRCLE because AUTO requires it; arming checks, land detector, auto-disarm, radio/GCS/battery/EKF failsafes; EKF3 + AHRS from IMU/baro/compass/GPS samples; MAVLink for QGroundControl 5.1.5), translated from ArduPilot's own sources, with a stub boundary that is the HAL plus the four sensor back ends.

**How big it is (measured, section 2).** The reduced vehicle (143 feature defines, appendix A; it builds, boots, initializes EKF3, arms and changes modes in SITL) has 112,850 reachable source lines (function extents of the live functions of the dead-stripped binary; 63,453 lines carry machine code). Of these:

| status | extent lines (code lines) | share |
|---|---|---|
| translated today (AC_PID, AC_AttitudeControl(+Multi), AC_PosControl, AP_Motors matrix, AC_WPNav, SCurve, SplineCurve, most of AP_Math and Filter) | 8,639 (4,848) + 964 (751) partly translated | 8.5 % |
| **to translate** | **58,073 (30,626)** | 51.5 % |
| stub boundary (of which 35,041 are the SITL simulator and SITL HAL, which the lock-step HAL replaces) | 42,671 (25,656) | 37.8 % |
| compile-out candidates still reachable | 278 (194) | 0.2 % |
| libc++ inline code | 1,679 (986) | 1.5 % |

So the port is about **6 times** what is translated today (58,073 / 9,603 extent lines; 30,626 / 5,599 code lines). At today's ratio of 1.87 Lean lines per C++ extent line, that is on the order of 100,000 lines of generated Lean. For comparison, the unreduced SITL ArduCopter has 281,773 reachable extent lines.

**What has to change in the translator before most of this can be translated** (section 4 and 5): (1) a whole-vehicle state ("World") with object identity, replacing the per-class `Inputs`/`Outputs`/live-read boundary between ArduPilot classes; (2) AST ingestion that does not load clang's whole JSON dump (one EKF3 or MAVLink-including translation unit is a 1.0 to 1.1 GB JSON document, 918 MB of it from the generated MAVLink headers); (3) byte-level objects (packed structs, unions, `memcpy`, storage images) for MAVLink, AP_Param and AP_Mission; (4) pointers to statically known objects (singletons, the `Mode *flightmode`, the init-time heap objects), functor tables, C strings and printf-style formatting, and bounded loops whose bound is not a syntactic constant.

**The three largest risks** (section 6.7): the architectural change to a whole-vehicle state across about 2,400 live functions; real-time speed of the Lean vehicle with FloatLib software floats and a double-precision EKF3 with two cores (QGroundControl needs real time); and the byte-level code of AP_Param and MAVLink (pointer arithmetic over `var_info` tables, packed structs, unions), on which bit-identical downlink bytes depend.

**Open decisions** are in section 7; the ones that shape the work are D1 (World model), D2 (reference board), D4 (EKF `ftype`), D11 (C library on the reference side) and D16 (what to do if the Lean vehicle is not real time).

## 3. The stub boundary

### 3.1 Principle

Everything ArduPilot does is translated; what stays outside is the HAL (the board) and the four sensor back ends, i.e. exactly what AP_HAL_SITL and the `*_SITL` back ends do in a SITL build. Both vehicles get them as **stand-ins with ArduPilot's class names and signatures**: in C++, a small lock-step HAL compiled in place of `libraries/AP_HAL_SITL` and of `AP_InertialSensor_SITL`, `AP_Baro_SITL`, `AP_Compass_SITL`, `AP_GPS_SITL` (the mechanism `ardupilot/standin/` and `cxx_overlay` already use); in Lean, the corresponding stub module that the translation calls at the same points. The SITL simulator (`libraries/SITL`, 29,541 reachable lines) is replaced by gym-pybullet-drones; only a `SITL::SIM` stand-in object remains, because SITL-board code reads a few of its members (below).

Time, threads and order follow SITL's lock-step HAL: one thread; the clock advances only at tick boundaries and in `delay` calls; timer and IO callbacks run where `HALSITL::Scheduler` runs them (`Scheduler.cpp:129-146`, `:230-306`); semaphores are no-ops.

### 3.3 Per-tick protocol (proposed successor of `sim/PROTOCOL.md`)

Phase 0: implemented as specified below except that every float is written as its bit pattern in hexadecimal (the input line is itself the bit-level trace), the line is `key=value` tokens, and there is no state digest yet; the format is in `reference/REFERENCE.md`. One input line per 400 Hz tick: the tick time; per IMU k triples of accel and gyro (k = samples per tick); baro pressure and temperature; compass field; a GPS record when a fix is due (else a marker); 16 RC PWM values and a flag; battery voltage and current; the uplink bytes received since the previous tick (hex, possibly empty). One output line: the motor PWM (and the four actuator values, for continuity with today's traces), the downlink bytes (hex), and with `--trace` a digest of the whole vehicle state (a hash of every leaf, so that a mismatch can be located by bisection). The Python side (gym-pybullet-drones) computes the samples from the rigid-body state with the formulas SITL uses (specific force, `AP_Declination` field, ArduPilot's atmosphere model), and bridges UDP to QGroundControl, timestamping each datagram to the tick at which it is delivered; the recorded input lines make every QGroundControl session replayable bit for bit.

## 4. Hard cases

### 4.0 Composition: from per-class boundaries to one vehicle state

Today each translated class sees the other ArduPilot classes as boundary objects (`Inputs`, `Outputs`, live reads), and `lean/Vehicle.lean` (667 lines) wires them by hand per tick. That does not scale to the whole vehicle: the live code makes 1,441 method calls and 682 member accesses through pointers, 325 calls of `gcs()`/`rc()`/`get_singleton()`, about 670 occurrences of `AP::...()` accessors in the source files of the modules to translate, and ArduCopter alone writes `copter.` 1,247 times; every edge would need hand-written glue, which the user does not want, and the calibration run (section 5.2) shows that even AC_Loiter and AC_Circle reject on boundary calls that the per-class model cannot express (non-const calls without arguments, calls with results).

**Proposal (D1).** Translate the vehicle as one program over one state. `World` is a structure with one field per statically allocated object (the global `copter` with everything it contains: `AP_Vehicle`'s members `ahrs`, `ins`, `gps`, `baro`, `compass`, `scheduler`, `serial_manager`, `notify`, `battery`, `g`, `g2`, the mode objects, `_gcs`, ...; the file-scope objects such as `mavlink_system`, `mavlink_comm_port[]`, `AP_Notify::flags`; the static locals) and one slot per init-time allocation site (4.10). A member function is translated against `World` plus the path of `this` (a lens); a call through a pointer or reference to an object whose identity is known at translation time (a singleton, a member bound in a constructor, a pointer assigned once at init) is a call on that object's path. The translator computes these identities by a closed-world points-to analysis over constructors, member initializers and init code, and rejects any pointer whose target set it cannot determine. Phase 3: no points-to analysis is needed: the world is closed by class, so a pointer of static type `B *` can point only to the file-scope and heap objects of B and its derived classes, all known to the translator (`--world-pointers`, README.md "Phase 3: World pointers, sensor front ends, HAL delays"); a call through it is a call on that object's path when there is one such object, else a `match` over them (a dispatch function); a member read through a pointer to several objects is rejected. Value-like classes (vectors, PIDs, filters, curves) keep today's functional `State` translation and nest inside `World` as they nest in C++, so the existing translations are reused; their per-class boundary inputs become reads of `World`.

### 4.1 The scheduler and its task table

`Copter::scheduler_tasks[]` (`Copter.cpp:115-260`, 66 entries before feature filtering) and `AP_Vehicle::scheduler_tasks[]` (`AP_Vehicle.cpp:641-722`, 30) are `const` arrays of `AP_Scheduler::Task { Functor<void> function; const char *name; float rate_hz; uint16_t max_time_micros; uint8_t priority; }` (`AP_Scheduler.h:88-94`), built by `SCHED_TASK_CLASS`/`FAST_TASK_CLASS` (`AP_Scheduler.h:46-63`) from `FUNCTOR_BIND(&copter.ins, &AP_InertialSensor::update, void)`. A `Functor` is an object pointer plus a pointer to a static trampoline `method_wrapper<T, method>` (`AP_HAL/utility/functor.h`). `AP_Scheduler::run` (`AP_Scheduler.cpp:191-300`) merges the two tables by priority with two offsets and calls `task.function()`.

**Proposal.** Every functor value in the program comes from a `Functor::bind<T, method>(obj)` instantiation whose object is a known path (4.0). The translator enumerates the binding sites (scheduler entries, the three AP_Mission callbacks bound in ModeAuto's member initializer, the IO/timer callbacks, the battery and GCS functors: 7 functor call sites in live code) and translates `Functor<R, Args...>` as an inductive with one constructor per site and `operator()` as a `match` that calls the bound method on its path. The task tables become constant arrays of that inductive; `AP_Scheduler::run` translates as written (its loop is bounded by `_num_tasks`, a member set once at `init`: loop with a fuel bound, 4.13). The `const char *name` stays a string literal. `fill_nanf_stack()` (SITL only, `AP_Scheduler.cpp:267`) writes NaNs into dead stack and has no effect on a program without uninitialized reads: dropped with a comment. The time budget logic (`_task_time_allowed > time_available`) is deterministic because the clock is the stand-in's.

### 4.2 The mode hierarchy

`Mode` (`mode.h:71`) has about 40 virtual member functions; the nine modes kept are member objects of `Copter`; `Copter::flightmode` is a `Mode *` assigned in `set_mode` from `mode_from_mode_num` (`mode.cpp:32-160`), which returns `&mode_auto` and so on, or `nullptr` for a compiled-out mode. Live code calls through `Mode *` about 110 times (`flightmode->run()`, `->requires_position()`, `new_flightmode->init(...)`).

**Proposal.** A pointer whose target set is a finite set of static objects of one class hierarchy is translated as a tag (an inductive with one constructor per possible object, plus `none` when `nullptr` is possible); a virtual call through it is a `match` that calls the final overrider of each object's dynamic class on that object's path; comparisons of such pointers compare tags. Virtual calls through `this` keep today's resolution. Mode members that are references or pointer references to Copter's objects (`Mode::Mode()` binds `g`, `g2`, `wp_nav`, `loiter_nav`, `pos_control`, `inertial_nav`, `ahrs`, `attitude_control`, `motors`, `channel_*`, ...) are constant paths. The same mechanism covers `GCS_MAVLINK *` channels (26 calls; channel objects allocated at init, 4.10) and the battery and notify back-end arrays. Phase 3: implemented as `inductive WPtr` (one constructor per file-scope object, one per heap class with the object's index, `null`) and per-call dispatch functions `WPtr.call'B'm` over the possible objects, computed from the pointer's type; tested on back-end arrays (`examples/worldptr.cpp`); `Mode *flightmode` needs nothing more (the modes are members of `copter`, which is F1's "objects that are members of a World object", still to do: they become World objects of their own or paths into `copter`). Phase 3 (AP_AHRS): the same need, met first in AP_AHRS, whose `AP_AHRS_Backend *configured_backend, *active_backend` and `Estimates *configured_estimates, ...` point to its own member objects (`&dcm`, `&ekf3`, `&sim`, `&dcm_estimates`, ...) and whose `backends_and_estimates[]` is a member array of structs of references to them: 67 of the 111 reachable rejections of the AHRS translation. Phase 3 (AP_AHRS translated): done as proposed, `--member-pointers` (README.md "Phase 3: AP_AHRS translated"): a `WPtr` constructor per member object of a World object whose address is taken or to which a reference member of an unnamed struct is bound; a call through a pointer or reference to them is a `match` on the tag over the running object's own members (each arm the call on that member, its final overrider), a read or write a member selected by the tag (all of one class); a reference parameter whose address is taken (or of an abstract class) and the reference members of `backends_and_estimates[]` are tags; the range-for over the reference array is a loop over the array of tags (not unrolled: `continue` works as written). Pointers to member objects are used only in the owner's member functions (the case for AP_AHRS; `Mode *flightmode` from Copter's member functions will be the same, through `copter`). A static data member of class type (`static NavEKF3 EKF3` of AP_AHRS_NavEKF3) is a World object (`--member-objects`, done).

### 4.3 Singletons

Each `AP::x()` and `X::get_singleton()` returns `*_singleton`, which the class's constructor sets (`_singleton = this`), usually with a panic if a second object is constructed. **Proposal.** The translator checks that exactly one object of the class is constructed in the closed world and maps the accessor to its path in `World` (for example `AP::ahrs()` to `copter.ahrs`, `gcs()` to `copter._gcs`, `AP::mission()` to `copter.mode_auto.mission`); `hal` is the stand-in's root. Accessors that may return `nullptr` (`AP::sitl()` before construction, `AP_InertialSensor::get_singleton()` which allocates on first call, `AP_InertialSensor.cpp:741`) are translated with their null check against the slot. Phase 3: a static singleton pointer of a class without a file-scope object is a World field (`C'_singleton : WPtr`) and the accessor that allocates on first call (`AP_DAL::get_singleton()`) is translated as written (a static function of the World, its `new` a heap slot); a class with a file-scope object keeps Phase 1's mapping (`AP_InertialSensor::get_singleton()` with a file-scope `ins` is that object). Singletons that are members of `copter` still need the accessor search inside World objects.

### 4.4 AP_Param

Phase 3 (NavEKF3): EKF3 reads scalar parameters of the front end through `frontend->` (done: the front end's `'p`), and AP_NavEKF_Source's `SourceSet _source_set[3]` holds `AP_Enum<SourceXY>` etc. parameters in an array of structs (AP_GROUPINFO into array elements): the AP_Param extension "parameters inside arrays of structs" is needed for it (`--param-ext`, the sensor front ends' stage, provides it; EKF3's translation does not use it yet); until then its getters are boundary-call inputs (README.md "Phase 3: AP_DAL and NavEKF3"). Phase 3 (fifth part): AP_NavEKF_Source is translated with `--param-ext` on its own and difftested (README.md "Phase 3: AP_InertialSensor, AP_GPS and AP_NavEKF_Source"); EKF3's translation keeps the boundary-call inputs until it is translated with `--param-ext` as a whole (its parameters become state), in the combined estimator stage.

How it works (read): each class has `static const struct AP_Param::GroupInfo var_info[]`, entries `{ name, ptrdiff_t offset = offsetof(Class, member), union { def_value; def_value_offset; group_info; group_info_ptr }, flags, idx, type }` (`AP_Param.h:133-154`, `:208`). The vehicle's top-level table (`ArduCopter/Parameters.cpp`, 79 `GSCALAR`/`GOBJECT`/`GOBJECTPTR`/`GOBJECTVARPTR`/`GGROUP` entries) gives each top-level object a key and an address; `GOBJECTPTR(wp_nav, ...)`, `GOBJECTPTR(loiter_nav ...)`, `GOBJECTPTR(circle_nav ...)`, `GOBJECTPTR(pos_control ...)` and `GOBJECTVARPTR(attitude_control/motors ...)` store the address of a pointer filled by `allocate_motors` (whose `var_info` depends on the frame). An `AP_Param *` is the address `base + offset` of an `AP_Int8`/`AP_Int16`/`AP_Int32`/`AP_Float`/`AP_Vector3f`; the code casts it by `ap_var_type` (`(AP_Float *)vp`). Enumeration (`first`, `next`, `next_group` recursive over nested groups, `next_scalar`, `AP_Param.cpp:1792-`), lookup by name (`find_by_name`, `:1003`), by index (`GCS_Param` walks `next` from a token), counting (`count_parameters`, `:2752`), name building (`copy_name_info`, `:847`, string concatenation into `char[AP_MAX_NAME_SIZE+1]`), and the storage format (`Param_header` bit-fields key:9/type:5/group_element:18 followed by the value bytes, scanned with `scan`/`find_by_header`, `:461`, `:784`) are all pointer and byte arithmetic. Enumeration is a runtime property: `AP_PARAM_FLAG_ENABLE` hides a group whose enable parameter is 0, and the vehicle-specific `var_info` of `motors`/`attitude_control` is chosen at init; so the order and count QGroundControl sees cannot be precomputed.

The scan of AP_Param's 95 live functions: 142 address-of/dereference, 95 pointer casts, 159 pointer parameters and locals, 73 member accesses through pointers, 38 C string calls, recursion in `next_group`.

**Proposal.** (a) Translate `var_info` tables as constant data (the translator already reads them for `--ap-param`); the `offset` of each entry is in the AST as `__builtin_offsetof(Class, member)` and becomes the field path. (b) A **parameter reference** type replaces `AP_Param *`: an inductive generated from the closed set of parameter objects in `World` (every `AP_ParamT`, `AP_Vector3f` and `AP_Enum` member reachable from the top-level table, including those behind the init-time pointers), with generated `get`/`set` by type and a `path` function; `base + offset` on an object path is path composition, `ptr == obj + offset` is path equality, `(AP_Float *)vp` is the typed accessor. (c) Everything else in AP_Param (the walks, name building, defaults, the conversion tables, `set_value`, `set_and_save`, storage scan) is translated from the source with these replacements, so enumeration order, names and counts are ArduPilot's. (d) The storage format is a byte-level object (4.5) over `StorageAccess`. (e) `save()` runs the IO-thread path (`save_io_handler`, registered with `register_io_process`, `AP_Param.cpp:1597`) at the points the stand-in scheduler runs IO callbacks. Oracle: for every index, name, type and value; for every name, the index; the storage bytes after `set_and_save`; all equal to the reference. Phase 3: for the front ends (`--param-ext`, README.md "Phase 3: sensor front ends and AP_Param") the parameter classes (`AP_ParamT`, `AP_ParamV`, `AP_ParamTBase`, `AP_Enum`) are translated from `AP_Param.h`/`AP_ParamT.cpp` as library classes, so a parameter is an object of the World's state at its member path (vectors, arrays of parameters, parameters in arrays of structs and in `RestrictIDTypeArray`s alike), (a) holds as written (`setup_object_defaults` from the table, entry by entry, with constant array indices; nested groups skipped as AP_Param skips them), and no parameter reference type is needed yet (the front ends never take an `AP_Param *`); (c)-(e) remain for Phase 4: storage is the boundary in the estimator's World (`save`/`notify` no effect, `configured()`/`load()` inputs, `set_default` sets unless configured), the boot values come from the vehicle's `load_all` (the replay takes them from the reference's probe). Parameters that the front ends write at run time (the barometer's ground pressure and field elevation, the compass's offsets, device ids and priority list) are state writes like any other.

Phase 4: done differently from (b), as the brief for this stage agreed (README.md "Phase 4: AP_Param"): no parameter reference type; AP_Param is translated over **one byte memory** (`--param-memory`, `cpp2lean_mem.py`, `support/ParamMemory.lean`), where `AP_Param *`, `void *ptr`, `ptrdiff_t` and `const GroupInfo *` are addresses (`UInt64`), the tables, their strings and the objects they point into (`copter`, `AP_AHRS_NavEKF3::EKF3`, ...) are bytes at fixed addresses, and `base + offset`, `(AP_Float *)vp`, `this == base + ofs`, `read_block(ptr, ...)` are what they are in C. (a) holds with a change: the tables are clang's evaluation of ArduPilot's initializers (the units' LLVM IR, serialized by the IR's data layout), not the JSON AST, whose `__builtin_offsetof` nodes carry no value; record layouts are clang's (`-fdump-record-layouts-complete`). ### 4.5 Mission storage, unions and packed structures

`AP_Mission` stores each command as a 15-byte record in the `StorageMission` area (`StorageManager.cpp:47-93` layouts; SITL uses the whole 32 KB; Phase 2: wrong, the reference board has `HAL_STORAGE_SIZE` 16384 and 15 areas, the mission areas 2422 + 2132 + 5204 bytes), converting through `Mission_Command { id; p1; union Content { ~40 structs }; }` and a packed form with `memcpy` (`AP_Mission.cpp:860-972`, `:3067`); `cmd_to_mavlink_int`/`mavlink_int_to_mission_cmd` convert to and from MAVLink; the execution state machine calls ModeAuto through three functors. EKF3 has two unions (`AP_NavEKF3_core.h:587` state array/struct, `:1621` a bit-field struct over an integer), AP_Param's `GroupInfo` has one, MAVLink's messages are packed structs, `mavlink_message_t` stores its payload as `uint64_t payload64[]` read as `char *`.

**Proposal: byte-layout objects.** A type marked for it (a translator option, or automatically for unions and `__attribute__((packed))` structs) is represented as a byte array of its `sizeof`, with field reads and writes at the offsets of clang's record layout (`-Xclang -fdump-record-layouts`, or the JSON AST's field types plus the ABI rules, checked against `sizeof`), little-endian, floats through their bit patterns (`Binary32.toBits`/`ofBits` exist in `CFloat.lean`), bit-fields by mask and shift. `memcpy`, `memset`, `memcmp` between such objects and byte arrays become byte-array operations with constant sizes. For unions of floats only (EKF3's `statesArray`/`stateStruct`), a cheaper **view** is enough: the array is canonical and `stateStruct.velocity.y` is `statesArray[5]` (an extension of the layout-prefix views the translator already has for `xy()`). Phase 3: the view is done (`--ekf-types`), and so are the bit-field unions over an integer (`nav_filter_status`, `nav_gps_status`, `gpsCheckStatus`), as the integer with each one-bit field a bit by mask and shift; a layout-prefix view of a member of the array view (`stateStruct.position.xy() = ...`, 5 statements) is not.

- **Arrays.** (Phase 3: done, `--ekf-arrays`, README.md "Phase 3: EKF data structures"; the 795 straight-line lines of `CovariancePrediction` translate, and need `set_option maxRecDepth` or a split into blocks: 520 statements in one `do` block exceed Lean's default recursion depth; elaborated with a raised limit in about 2.8 s, they run in 783 µs per call.) ### 4.7 The MAVLink C library

**How ArduPilot generates it.** `wscript:781` runs waf's `mavgen` tool (`Tools/ardupilotwaf/mavgen.py`), which calls pymavlink's `mavgen` with language C and wire protocol 2.0 on `modules/mavlink/message_definitions/v1.0/all.xml` (ArduPilot's fork `ArduPilot/mavlink` at e03dad40, pymavlink eb88edf2; not the upstream checkout at `/Users/ryan/Research/delegate/mavlink`, whose XML differs) into `build/<board>/libraries/GCS_MAVLink/include/mavlink/v2.0/` (one directory per dialect; `common` alone has 211 headers; common + ardupilotmega + minimal + standard are about 150,000 lines). `GCS_MAVLink.h` configures it: `MAVLINK_SEPARATE_HELPERS`, `MAVLINK_USE_CONVENIENCE_FUNCTIONS`, `MAVLINK_SEND_UART_BYTES` = `comm_send_buffer` (which writes to `mavlink_comm_port[chan]`), ArduPilot-provided channel buffers and status (`MAVLINK_GET_CHANNEL_BUFFER/STATUS`), 16 channels on SITL.

**What the code does (verified by preprocessing).** `MAVLINK_ALIGNED_FIELDS` is 1 and the target little endian, so `mavlink_msg_X_send` fills a packed `mavlink_X_t` and passes `(const char *)&packet` to `_mav_finalize_message_chan_send`; `mavlink_msg_X_decode` does `memset(struct, 0, LEN); memcpy(struct, _MAV_PAYLOAD(msg), len)` (zero-extension of truncated MAVLink 2 payloads); `_MAV_RETURN_T` getters `memcpy` from the payload; `_MAV_PAYLOAD(msg)` views `uint64_t payload64[]` as `char *`. The helpers in `mavlink_helpers.h` are byte-level C: header packing, payload trimming, CRC (`crc_accumulate`, X.25, with the per-message `crc_extra` from `mavlink_get_msg_entry`, a binary search over a static table), the parser `mavlink_frame_char_buffer` (one 348-line state machine over one byte per call), signing (compiled out). Live: 148 generated message functions (58 messages sent, 40 decoded) and the helpers, 4,120 extent lines. Phase 4: wrong in three points. (1) Signing is not compiled out of the library: `MAVLINK_NO_SIGN_PACKET` is not defined, so `mavlink_sign_packet`, `mavlink_signature_check` and the SHA-256 code are compiled into GCS_MAVLink.cpp; `AP_MAVLINK_SIGNING_ENABLED 0` only removes GCS_Signing.cpp, the one place that sets `mavlink_status_t::signing`, so the pointer is always null and the signing paths are dead (the translation folds them, `--null-member`; the parser's signed-frame states stay live: a frame with the SIGNED flag waits for 13 signature bytes). (2) The fork's `mavlink_message_t` is a packed 298-byte struct with a 32-bit `sysid`, a bit-field `uint32_t msgid:24`, `payload64[33]` and a `target_sysid` (SYSID32 and TARGET32 extended headers), and the parser has 24 states; `mavlink_frame_char_buffer` is 354 lines. (3) `mavlink_channel_t` is the library's enum of four values (`HAVE_MAVLINK_CHANNEL_T` is not defined): ArduPilot casts channel numbers up to 15 into it (`(mavlink_channel_t)(MAVLINK_COMM_0 + i)`), which a translation of the enum as its four enumerators cannot represent: the GCS translation needs the enum as its integer (the Phase 4 tests use channels 0-3). Also: not every message struct is packed (`mavlink_param_set_t` is 24 bytes with padding, its wire length 23); decoders of messages with a target system call `mavlink_msg_decode_target` (TARGET32), the others `memset`/`memcpy`. Done (README.md "Phase 4: the MAVLink C library"): the helpers and 48 messages' functions translated from the generated headers, difftested bit for bit.

**Can it be translated?** (Phase 4: yes, done as proposed; the byte-layout objects are the struct values with their layouts, converted where the code views them as bytes, and `payload64` stored as its bytes; README.md "Phase 4: the MAVLink C library".) Yes, with translator intrinsics for byte access, not by hand: (a) the packed message structs and `mavlink_message_t` as byte-layout objects (4.5), so that `memcpy` between a struct and the payload is (de)serialization at the record layout's offsets, which the generated `MAVLINK_MESSAGE_INFO_X` tables can cross-check; (b) `char *`/`uint8_t *` arguments into arrays as (array, offset) slices, `buf[i]` through them, and `(const char *)&packet` as the struct's byte view; (c) `strncpy` into fixed `char[N]` fields (`param_id`, `text`) as byte-array copies. The parser, CRC and finalizer then translate as ordinary code over `UInt8` arrays. The alternative, a Lean codec generated from the XML by our own generator, would put new code in place of ArduPilot's generated code; not recommended (D14).

Phase 4: GCS_MAVLink is translated over the byte memory of AP_Param (`--param-memory`, `ardupilot/gcs/GCS.json`, README.md "Phase 4: GCS_MAVLink"), not over the value World: the generated MAVLink helpers the GCS uses are translated a second time there (the value translation `Mavlink_lib` stays the difftested one), the objects' dynamic classes (`GCS_Copter`, `GCS_MAVLINK_Copter`, `MissionItemProtocol_Waypoints`) are configuration (`dynamic`), and `mavlink_channel_t`'s four enumerators are no limit there (a channel is a byte). The byte replay against the recorded sessions is not done yet.

### 4.8 Text: STATUSTEXT, names, formatting

Live code has 701 string literals, 151 calls of C string and formatting functions (`snprintf` 59, `printf` 29, `strlen` 12, `strncpy` 9, ...), 46 `char[N]` buffers, and about 350 user-visible text call sites (`GCS_SEND_TEXT` 129, `check_failed` 126 for the PreArm/Arm messages QGroundControl shows, `send_text` 93), 206 of them with `%` formats. `GCS::send_text` formats with `hal.util->vsnprintf`, which is ArduPilot's own `print_vprintf` (`AP_HAL/Util.cpp:46-55`, `AP_HAL/utility/print_vprintf.cpp`, `ftoa_engine.cpp`, `utoa_invert.cpp`, 464 code lines: integer code, floats to decimal included). Other code calls the C library's `snprintf` directly (names of parameters and sensors, `AP_NavEKF3.cpp:1189-1202`).

**Proposal.** `char[N]` and string literals are byte arrays with C-string semantics; `strlen`, `strncpy`, `strcmp`, `strncmp`, `strncasecmp`, `strnlen`, `memcpy`, `memset`, `memcmp` are a small runtime with their C semantics, difftested against the C library as `CppLibm` was. Variadic calls with a literal format become a call with an argument list of tagged values; `va_list` functions (`print_vprintf`, `GCS::send_textv`, `AP_Arming::check_failed`) translate over that list. `print_vprintf` is translated from ArduPilot; the C library's `snprintf` is routed either to the same runtime or to a translated formatter for the subset of formats used, difftested against the reference's C library (D10).

### 4.9 Time-dependent code

241 clock reads in 193 live functions, timeouts everywhere (failsafes, GPS lag, EKF timing, MAVLink streams and retries, mission upload timeouts, land detector), and the scheduler's time budget. In SITL the clock only moves in `delay` and between ticks, so every read within a tick returns the same value; the stand-in does the same in both vehicles, which makes all of it deterministic and comparable. `wait_for_sample` (`AP_InertialSensor.cpp:2025-2120`) calls `delay_microseconds_boost(wait_usec)` to the next sample time and then loops until samples are present; with the samples of the tick delivered before the loop iteration, the loop exits on its first pass. `get_hw_rtc` must not return wall time (SITL does). Phase 3: confirmed in the replay of the sensor World (README.md "Phase 3: AP_InertialSensor, AP_GPS and AP_NavEKF_Source"): in every main loop of both recorded flights `wait_for_sample` consumes no line; inside `ins.init`'s gyro calibration it does (`update()` implies a wait). The loop has no bound: without input records it does not end (in C++ as in Lean), so a harness keeps records fed. Nothing reads a random source on the paths of interest except MAVLink signing (compiled out); a deterministic stand-in for `get_random16` covers the rest.

### 4.10 Heap allocation at start-up

Live `new`/`malloc` sites (36 `new`, 11 `delete`, plus `malloc_type`/`calloc`): `Copter::allocate_motors` (`system.cpp:387-497`: motors, attitude, position, waypoint, loiter and circle controllers), `AP_AHRS_Backend::create_view` (`AP_AHRS_Backend.cpp:171`), the EKF3 cores and their buffers and `EKFGSF_yaw`, `AP_DAL` and `AP_InertialSensor` singletons, the GCS channels (`GCS_Copter.h:43`, one per MAVLink port at `setup_uarts`), `MissionItemProtocol_Waypoints` (allocated lazily at the first mission transfer, `GCS_Common.cpp:2754`), the scheduler's `_last_run` and `PerfInfo` arrays (`AP_Scheduler.cpp:135`, `PerfInfo.cpp:48`), AP_Param's defaults lists (only with a defaults file), the sensor back ends (boundary) and the notify devices (none). ArduPilot never frees these except on init failure (`GCS_Common.cpp:2842`).

**Proposal.** Each allocation site in reachable code becomes a slot in `World` (an `Option T.State`, or an array of fixed capacity for per-instance sites such as cores and channels); `new` fills it, `nullptr` tests read it, `delete` clears it. Allocation never fails in the model; `allocation_error` (which panics) is unreachable and is translated as the halt of 4.13. The translator rejects a site executed twice into the same slot unless it is an array site. Phase 3: simpler and as faithful: one slot array per class (not per site), `heap'C : Array C.State`, in creation order; `new` appends (a site in a loop, `for (i < sitl->baro_count) _add_backend(NEW_NOTHROW AP_Baro_SITL(*this))`, needs no capacity); `delete` leaves the slot (ArduPilot frees only back ends whose init failed, which nothing refers to again); placement new into `--heap-alloc` memory (`malloc_type`) constructs into reserved slots. A constructor may reach the World (back ends register with their front end and the scheduler).

### 4.11 Threads and semaphores

32 `WITH_SEMAPHORE` sites in live code, `register_io_process` (AP_Param saving, `AP_Param.cpp:1597`), `register_timer_process`, `register_timer_failsafe` (Copter's main-loop watchdog `failsafe_check`, registered at `system.cpp:86`, `failsafe.cpp:35`). Semaphores are no-ops and callbacks run at the stand-in scheduler's defined points (Phase 4: AP_Param's IO callback `save_io_handler` and its queue are not translated yet, README.md "Phase 4: AP_Param"), which is SITL's single-threaded lock-step semantics. This is faithful to SITL, not to a multi-threaded flight controller; the reference vehicle has the same semantics, so bit identity is unaffected. Phase 3: done as `--semaphores` (members and `WITH_SEMAPHORE` locals of the named classes are no state and no statement, `take`/`give` succeed); `register_timer_process` with functors is implemented for the HAL stand-in (a narrow F3: `Functor<void>` as `inductive WFun` over the program's `FUNCTOR_BIND`s).

### 4.12 Size of clang's AST

The translator reads clang's whole JSON dump with one `json.loads` (`cpp2lean.py:4884-4891`). With the real headers, a translation unit that includes `GCS_MAVLink.h` (directly or through AP_Logger, AP_DAL, AP_Mission, ...) produces about 1 GB of JSON, 918 MB of it the generated MAVLink inline functions; Python needs several times that in memory, and this machine has 16 GB. Today's translations avoid it with hand-written stub headers (`ardupilot/stubs/`); for the whole vehicle the stubs would have to declare most of ArduPilot (the calibration run already needed two more declarations).

**Proposal.** (Phase 1: done as proposed, in two passes over the dump on disk; README.md "Streaming AST input": 1 GB dumps in about 9 s and 300 to 550 MB.) Stream the dump: read clang's stdout incrementally, decode the translation unit's top-level declarations one at a time (`json.JSONDecoder.raw_decode`), and keep only those in the translated and library files plus the declarations they reference (MAVLink message functions only when called); the location state that clang's JSON elides must be tracked across the skipped declarations. `-Xclang -ast-dump-filter=<name>` is a working fallback (verified: a filtered dump of `NavEKF3_core::` is 69 MB and takes about half a second), but it filters by name, not by reachability.

### 4.13 Control flow and Lean performance

- Phase 3 (NavEKF3): no loop of EKF3, AP_DAL or AP_NavEKF needed fuel: `i <= stateIndexLim` has the value range of a member whose every write is a constant (0..23), nested `c <= r` the range of the outer counter, `ARRAY_SIZE` is a constant. Two Lean limits: a body of 520 straight-line statements (and NavEKF3_core's constructor) needs `maxRecDepth` 200000 in the code generator (20000 is not enough); a run of 15 consecutive `pure ()` statements in a `do` block makes elaboration exponential (not finished in 10 minutes), so the translator must not emit runs of no-op statements. Speed of the translated EKF3 (one core): 0.22 ms per 400 Hz UpdateFilter on average, 1.0 ms per prediction step (p99 3.5 ms); 86% of it is array copying (pointer arguments into P passed as slices and spliced back by `zero_range`, and heap objects passed while still in their slots), not FloatLib arithmetic (9%). Phase 3 (speed): both copies removed (`--array-offsets`: a pointer is the array and an offset, written back whole; `--swap-out`: a heap or World object's state is taken out of the World for a call that writes it; README.md "Phase 3: AP_AHRS, and speed"): one core 0.13 ms per step on average, 0.57 ms per prediction step (p99 2.0 ms), two cores 0.27 ms and 1.16 ms (p99 4.1 ms); array copying is now under 1% and FloatLib's `Binary64` arithmetic 84%, 61% of the whole in FloatLib's model fallback on `Nat` (GMP), which its word kernels take for zero operands (`addFieldsWord?` declines a zero significand) and EKF3's arithmetic has many. The next factor is in FloatLib (word paths for those inputs) or in `support/CFloat.lean` (`@[csimp]` fast paths with proofs), not in the translator.
- **Loops without a syntactic trip count**: 108 `while`/`do` loops, 20 range-`for` loops, and many of the 485 `for` loops bound by runtime counts (`_backend_count`, `_num_tasks`, `num_cores`, table lengths). Phase 2: every loop of the Phase 2 libraries has an exact trip count derivable from the C++ types (`--runtime-loops`), so no fuel was needed there. Proposal: a loop is translated with a fuel bound the translator derives (array lengths, `uint8_t` ranges, table sizes) or that the configuration declares; running out of fuel is an explicit error outcome, which the difftests show never happens. Recursion (`AP_Param::next_group`, `find_var_info_group`) gets a depth bound (the nesting depth of the `var_info` tables).
- **goto**: 9 forward `goto`s in 4 functions (`AP_InertialSensor.cpp:1631`, `:1639`, `:2046`; `AP_Mission.cpp:2820`, `:2865`; `StorageManager.cpp:359-377`): translated as structured forward jumps (skip to the label within the same block).
- **Non-termination**: `AP_HAL::panic`, `AP_BoardConfig::config_error` (loops forever printing), `allocation_error` (44, 13 and 13 call sites in live functions): a `Halted` outcome of the tick, reported by the harness.
- **Static locals and globals**: 39 static locals in 22 live functions (`AP_Vehicle.cpp:745` `last_1hz`/`last_50hz`/`last_5s`, `AP_NavEKF3.cpp:965`, `GCS_Common.cpp:2554`, constant tables), and file-scope objects: fields of `World` (constant ones stay `def`s).
- **Lean arrays in nested state**: `{ s with P := s.P.set! i v }` shares `s.P` with `s` and copies the array on every write unless the translator first moves the array out of the structure. For 24×24 EKF matrices updated element by element that is the difference between O(1) and O(576) per write. The translator must emit the swap-out pattern for array members it updates in loops; measure early (Phase 1). Phase 3: wrong for arrays held by structures: Lean's compiler reuses the projection's reference when `s` is unique, so `{ s with P := s.P.set! k v }` and `{ s with a.P := ... }` update in place (4.9 ns per element write of a 24×24 `Binary64` matrix, `lean/F15Bench.lean`); right for an array reached through an element of another array (`s.EKF[m].P[k]`: 639 ns per write, a copy each time), for which `--ekf-arrays` now emits the swap-out (10.4 ns; README.md "Phase 3: EKF data structures"). Phase 3 (speed): two more cases copied whole arrays, both measured in the EKF3 translation, not in the bench: a slice passed for a pointer into an array (`a.extract k a.size`, spliced back), and a heap object's state passed while still in its slot (shared, so each of its arrays is copied on its first write in the call); `--array-offsets` and `--swap-out` remove them.
- **Floating point**: the retarget to FloatLib (`lean/CFloat.lean`) translates libm from musl's sources, so the C++ reference must link musl's libm too for bit identity (D11). EKF3 in double adds `sin`, `cos`, `atan2`, `asin`, `sqrt`, `pow`, `exp`, `log` at `Binary64`.

Sizes are extent lines to translate, and their ratio to the 9,603 extent lines (8,639 translated + 964 partly) behind today's 17,920 Lean lines. ### 6.7 Risks, and what cannot be translated faithfully

Largest risks:

1. **Architecture and scale.** The `World` model, the points-to analysis and the byte-level objects are a different translator from the per-class one, and ArduPilot's style (singletons, pointers set at init, virtual calls, functors) is everywhere: 1,441 calls through pointers in 2,442 live functions. Mitigation: Phase 1 before any new module, with the existing seven translations as the regression oracle.
2. **Speed.** QGroundControl's timeouts are in wall time (3.5 s heartbeat loss, 5 s parameter list, 1 to 1.5 s acknowledgements), so a QGroundControl session needs the Lean vehicle in real time: 400 ticks per second with two double-precision EKF3 cores (on the order of 10^4 double operations per core per tick, estimated from the size of the prediction and fusion code), GCS streaming and the controllers, all on FloatLib software floats, plus Lean's array copying if F15 is not done. Today's Lean vehicle needs about 10 µs per tick with hardware floats against 1 µs for the C++ (`sim/BENCH.md`). Mitigation: measure in Phase 0; options in D16. Phase 1: the Lean controllers now take about 0.1 ms per tick (from 2.88 ms): FloatLib's comparisons and literal roundings were the cost, not its arithmetic; what remains slow are the float/integer and double-to-float conversions of variables (rational arithmetic), whose bit-level proofs were not done. Phase 0 measured the C++ side: the whole reference vehicle takes 3.4 µs per step on average (3.9 µs flying), of which AHRS and EKF3 take 0.69 µs (one double core; EKF3 down-samples the IMU to its 12 ms prediction step, `EKF_TARGET_DT`, `AP_NavEKF3_core.h:56`), so the Lean vehicle may be up to about 700 times slower than the C++ and still run in real time; the Lean side's factor is the open number.
3. **Byte-level code.** AP_Param's pointer arithmetic over `var_info`, MAVLink's packed structs and payload views, AP_Mission's unions and storage format are the least control-like code and decide the downlink bytes QGroundControl sees. Mitigation: the byte-layout objects of 4.5 with record layouts taken from clang, cross-checked against `MAVLINK_MESSAGE_INFO`, and the Phase 4 difftests before integration.

Further risks: Lean elaboration time of very long generated functions (`CovariancePrediction`, 795 lines; `mavlink_frame_char_buffer`, 348); the C++ reference's C library (D11).

Cannot be translated faithfully, and what to do instead:

- **Multi-threaded execution** (IO and timer threads, semaphores): not modeled; the vehicle runs SITL's single-threaded lock-step semantics in both implementations (4.11).
- **Non-terminating paths** (`panic`, `config_error`, `allocation_error`): a `Halted` outcome (4.13).
- **Wall-clock time** (`get_hw_rtc` on SITL): replaced by simulated time in both vehicles.
- **Undefined behavior** (uninitialized reads, which SITL's `fill_nanf_stack` exposes): excluded, as today. Phase 4: one kind is not excluded but compiled to a definite result the model must reproduce: a float converted to an 8- or 16-bit integer out of range is `fcvtzs w` and truncation on the reference target (arm64), `(uint8_t)-221.0f` = 35, where CFloat's `Binary32.toUInt8`/`toInt8`/`toUInt16`/`toInt16` saturate to the narrow range (0, 255, ...); AP_Mission's conversions reach it with any MAVLink float, so `--mission` converts through `Binary32.toInt32` (README.md "Phase 4: AP_Mission"); the earlier translations keep CFloat's and differ from the reference only for out-of-range values. Reading a `bool` from a byte other than 0 or 1 (a stored DO_ENGINE_CONTROL from a corrupt or foreign storage image) is excluded: clang converts the byte itself.
- **NaN payloads**: not observable in FloatLib's or Lean's floats either way; handled by the existing NaN rule.
- **The C library** (`snprintf`, `strtof`, libm): not ArduPilot code; a translated runtime (musl's libm already, per `CFloat.lean`) whose bit identity rests on the reference linking the same implementation (D11) and on difftests.
