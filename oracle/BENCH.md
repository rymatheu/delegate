Generated by `oracle/bench.py`; do not edit by hand. Inputs: the recorded 1 m/s course, `sim/out/copter-course-1ms/copter-bin/inputs.txt` (8431 ticks), parameters `sim/params/copter-cf2x.txt`, `sim/params/copter-course-speed.txt`; the oracle reads the navigator targets from `trace.txt` and switches AutoYaw to HOLD at tick 6618.

Machine: Apple M4, macOS 15.6.1 (24G90), 17179869184 bytes RAM; Apple clang version 17.0.0 (clang-1700.6.4.2); Lean leanprover/lean4:v4.33.0-rc1. Date: 2026-11-04 12:27.

## Protocol

Both programs parse every input line first (the oracle also the navigator targets), set the parameters, build the objects and apply the takeover with the first sample, untimed; then they run 3 warm-up passes over all ticks, 20 passes timed around the whole tick loop (per-tick mean = loop time / ticks; mean and sample standard deviation over the 20 passes), and 20 passes timed around each tick (median, p99 and max over the 20 x ticks samples). Each pass starts from the same initial state (the port: the same taken-over `State`, threaded through `Copter.loop`; the oracle: fresh objects per pass). Nothing is printed per tick; the checksum, the XOR of the bit patterns of the four actuators over all ticks of a pass, is printed at the end. Clocks: `IO.monoNanosNow` (Lean) and `std::chrono::steady_clock` (C++), both read the same macOS monotonic clock, whose resolution on this machine is 1/24 MHz = 41.7 ns; the per-tick distribution is quantized to that step (a timer read costs less than one step: the median of two consecutive reads is 0 in both programs). Each program was run 5 times, alternating. Load average when the runs started: 3.93 4.27 4.45; other jobs were running on the machine (it is shared with other agents' builds and simulations), and macOS may place a process on an efficiency core under load, so single passes can be slow; the median of the pass means is the robust figure.

Builds: the port by `lake build bench` (Lean to C, then `leanc` = the toolchain's clang at `-O3 -DNDEBUG` with the lakefile's `moreLeancArgs`, i.e. `-fno-builtin-sinf -fno-builtin-cosf` and whatever else the lakefile adds); the oracle by `oracle/build.sh nosincos` (Apple clang, `-O2 -ffp-contract=off -fno-fast-math -fno-builtin-sinf -fno-builtin-cosf`, flags unchanged). The C route of `sim/build_copter_c.sh` was not used for `bench`: its root module (`Copter.Main`) and lake target are fixed in the script, and adapting it would mean editing `sim/`. `lake exe bench` is native code compiled through C already, at the same `-O3`.

## What the two ticks contain

The oracle's tick is the cascade of `oracle/main.cpp`: scheduler step and gyro, `rate_controller_run` and `rate_controller_target_reset`, `motors->output()`, the AHRS view update, `update_estimates`, on the first tick the `wp_and_spline_init_m` calls and rate time constants, the AutoYaw choice, `set_pos_terrain_target_D_m`, `set_pos_vel_accel_NED_m` with the navigator's targets **read from an array** (parsed from the port's trace), `NE_update_controller`, `D_update_controller`, `input_thrust_vector_heading`.

The port's tick is `Copter.loop`, which also **runs the navigator and the mission logic**: `ModeAuto.run` calls `mission_update` (waypoint verification and sequencing) and `AC_WPNav.update_wpnav` (speed-change checks, `advance_wp_target_along_track` with the `SimplePath` leg sampling, then `NE_update_controller`), and `AutoYaw.get_heading`. So the port does strictly more work per tick. Segment timing (`bench`, separate passes, timer reads between segments; mean ± sd over the runs):

| port segment | ns per tick |
|---|---|
| `Copter.loop` up to `read_inertia` and the Auto switch (scheduler, gyro, rate controller, motors output, AHRS view, estimates) | 980.8 ± 37.1 |
| `update_flight_mode` (`ModeAuto.run`: mission, navigator, position and attitude controllers) | 2469.8 ± 55.0 |
| navigator alone, side computation on the same state (`mission_update` + `advance_wp_target_along_track`) | 448.4 ± 10.6 |

The navigator side computation shares the state with the real tick, so the records it updates are copied rather than updated in place: 448 ns is an upper estimate of what the navigator adds to the port's tick. Subtracting it from the medians of the pass means, the port's control cascade alone costs about 3004 ns per tick, 4.12 times the oracle's 729 ns.

Other differences that bear on fairness:

- Optimization levels differ: the port's C is compiled at `-O3` (lake's default), the oracle at `-O2` (`oracle/build.sh`, unchanged); both keep strict IEEE semantics (`-ffp-contract=off` in `leanc`, no fast-math).
- The port is a pure function on a `State` record of nested structures: each `{ s with ... }` update reuses the object in place only when its reference is unique and otherwise allocates a copy, and values returned in pairs (`(state, output)`) can be allocated as tuples; the C++ updates the members of four heap objects in place. The arithmetic is the same IEEE `float`/`double` operations on both sides (the checksums agree; `oracle/compare.py` checks the outputs value by value); where the rest of the gap goes (allocation, reference counting, copying) was not profiled.
- The oracle sets parameters on its objects once per pass; the port reads its `Parameters` record (passed by reference) on every tick. Neither cost is in the tick loop beyond field reads.
- The first tick of each port pass starts from a shared `State` (the same `s0` for every pass), so it copies the records it updates; one tick in 8431, negligible.
- Both run single-threaded on an otherwise idle machine; no CPU pinning or frequency control is available on macOS, so the p99 and max columns include scheduler and interrupt noise.

The ticks themselves take 0.029 s of each run (8431 x 3492 ns, 2.1% and 0.6%); the rest is the line parsing, the non-exact printing and process startup. Likewise the oracle's 0.30 s is almost all I/O: its ticks take 0.0064 s.
